## 1. 项目定位与核心主张

SynthForge Studio 是一款本地桌面 AI 游戏开发工作站：同一软件内划分两个相对独立的工作区——「Blender 建模区」与「Unity 游戏区」，右侧常驻 AI 对话区全程协同。用户可以在同一软件里专注做美术（AI 低模建模或 3D 云 API 生成），或专注做游戏（自然语言驱动 Unity 编辑器）。

核心主张：

1. **建模与做游戏相互独立**：各自有目录、会话、工具集，互不干扰。
2. **资产流转显式可控**：不做自动偷跑的流水线；用户在 Unity 区主动选择建模资产，交给 agent 导入进游戏。
3. **两个 AI 入口统一配置**：设置里分「Agent 模型」与「3D 模型」两栏，预置服务商 Base URL 写死，自定义才显示 Base URL。
4. **核心与 UI 解耦**：C++ 核心可在无界面模式下独立运行（开发调试友好），网页 UI 通过一条本机 WebSocket 通道与之通信。

## 2. 范围界定

### 2.1 v1 做什么

- 侧边栏式三区布局：活动栏（blender / unity 切换）+ 资源管理器 + 中间预览区 + 右侧常驻对话区。
- Blender 建模区：固定资产库目录、右键分类文件夹；两种建模模式（低模 = Blender MCP 直操、3D 云 API = 混元3D / Tripo / 自定义）。
- 提示词总结 agent：把口语化需求改写为专业提示词，以可编辑草稿形式确认后再生成。
- Unity 区：自选游戏工程、单一激活工程互斥切换、文件变更双源同步、Unity MCP 对话驱动（建物体 / 脚本 / 组件 / 截图 / Console 回读）。
- 跨区资产流转：「添加资产」选择器 → glb 自动经 Blender 转 fbx → Unity MCP 导入实例化。
- 两栏式设置（Agent 模型 / 3D 模型）、配置本地持久化、会话持久化、任务日志。
- Windows 桌面单 exe 分发（Qt + WebEngine）。

### 2.2 非目标（未来方向）

- 骨骼绑定、Text2Motion 动作生成的扩展 MCP（旧文档的动画扩展部分）。
- 建模完成自动导入 Unity 的 DAG 流水线（v1 全部由用户显式发起）。
- 多会话管理（v1 每区单线程）、多 Unity 工程并行、Unreal 引擎支持。
- 资产版本管理 / 回滚、缩略图缓存、批量资产生成、本地 Ollama。
- 主题切换、多语言（v1 中文界面、深色主题优先，视觉打磨后置）。

## 3. 技术选型

### 3.1 选型结论

| 层 | 选择 | 说明 |
|---|---|---|
| 语言 | C++20 | 核心与外壳全部 C++ |
| GUI 框架 | Qt 6（Widgets 外壳 + Qt WebEngine） | 主窗口、原生对话框、内嵌网页 UI |
| 前端 | Vue3 + TypeScript + Vite | 活动栏 / 文件树 / 预览 / 聊天面板 / 设置 |
| 3D 预览 | three.js（GLTFLoader + OrbitControls） | 加载 GLB，旋转 / 缩放 / 平移 |
| MCP 客户端 | **自研**（JSON-RPC 2.0 over stdio） | C++ 学习核心：进程通信 + 协议编解码 + 异步状态机 |
| 前后端通信 | 本机 WebSocket（QWebSocketServer，127.0.0.1 随机端口 + token） | 双向 JSON 消息 |
| LLM 协议 | OpenAI 兼容 chat/completions（流式 SSE + tool_calls） | 一套代码通吃全部预置服务商 |
| 网络 / JSON | QNetworkAccessManager / QJsonDocument | 不引入额外第三方库 |
| 本地存储 | SQLite（Qt SQL 自带 QSQLITE 驱动）+ settings.json | 会话 / 草稿 / 任务记录；无额外第三方库 |
| 构建 | CMake + MSVC（Qt WebEngine 在 Windows 必须 MSVC 工具链） | 前端另用 npm/Vite 构建 |

### 3.2 取舍记录

- 对比过 **Go + Wails**（原文档方案）与 **Electron + TS**、**Tauri + Rust**：因导师建议走 C++ 方向且项目要求桌面客户端，最终选 **C++ 核心 + 网页 UI** 混合；C++ 覆盖最有含量的核心逻辑（MCP 客户端、进程管理、LLM 网关、任务调度），UI 用网页技术保证质量与迭代速度。核心与 UI 经消息协议解耦，未来换 UI 技术栈时核心无需重写。
- 对比过 **Qt 全原生 UI**（Widgets/QML）：聊天区富文本 / 流式 / 工具卡片在 Qt 里自研成本高、精细度上限低；网页 UI 成熟省力。资源管理器、窗口等外壳仍由 Qt 承担。
- 此架构与 VS Code 互为镜像：VS Code 是 JS 应用跑在 C++ 运行时上；本项目是 C++ 应用托着网页 UI。

### 4.2 顶部栏

- **"导入"按钮**：unity 区时点击选择 Unity 游戏工程文件夹（校验含 `Assets/` 与 `ProjectSettings/`，不合格明确拒绝）；blender 区时显示固定资产库路径（只读，不可改）。
- **状态灯两盏**：`●Blender`、`●Unity`，各自代表"后端→桥接进程→插件→握手"整条链路状态（灰=未连接、绿=就绪、黄=重连中）；鼠标悬停显示具体卡在哪一步（如"Blender 未启动"/"插件未在 Blender 中运行"/"已就绪 · 42 个工具"）。
- 不设笼统的"MCP 灯"；每盏灯本身就是 MCP 连接状态展示。

### 4.3 左侧活动栏

- 上部：blender 图标、unity 图标，点击切换右侧三栏的工作区视图。
- 底部：设置齿轮（打开设置对话框）。

### 4.4 资源管理器

- blender 区 = **模型资产库**（固定路径 `文档\SynthForgeStudio\ModelLibrary`，不可选）。
- unity 区 = **游戏工程**（用户自选，显示工程文件树）。
- 右键菜单统一为：新建文件夹 / 重命名 / 删除（二次确认）/ 在系统资源管理器中显示 / 刷新。

### 4.5 预览区

- blender 区：选中资产 → three.js 加载 GLB，可旋转 / 缩放 / 平移；生成完成后**自动加载**新资产；未选中 → 资产库概览卡片。
- unity 区：选中文件 → C# 代码高亮预览 / 图片预览 / 文本预览；未选中 → 工程信息卡（路径、最近一次 Game 截图入口）。

### 4.6 对话区

- 永远位于最右侧；blender 会话与 unity 会话**互相独立**（历史、上下文、可用工具各不相同），各自持久化。
- **两个常驻对话面板**：blender 区与 unity 区各持有一个常驻 `ChatPanel` 实例（切区只做 `v-show` 显隐，不卸载、不重建、不重新加载历史）。消息、流式输出、进行中状态（停止按钮）、草稿卡 / 计划卡 / 错误卡均按区保存在各自实例中：任一区在后台产生的事件不会丢失，也不会串到另一区。
- **会话上下文**：每次发起新任务时自动携带本区最近 20 条历史消息（纯文本，不含截图 base64；超预算从最旧截断）组装 LLM 上下文；两区历史互不可见。
- 顶部显示当前区名；blender 区额外显示当前建模模式（低模 / 云 API）与云 API 配置徽标（未配置 / 已配置）。
- 消息形态：普通文字、工具调用步骤卡（可折叠）、截图图片、资产产出卡（[查看] 按钮 → 预览区加载）、**专业提示词草稿卡**（可编辑，见 5.2）、**建造计划卡**（分组 / 清单 / 验收标准，见 5.3）。
- 对话区头部右侧提供"清空本区对话"按钮（二次确认）。

### 4.7 设置入口

- 活动栏底部齿轮 → 设置对话框（两个标签页：Agent 模型 / 3D 模型，见第 7 节）。

## 5. 建模区（Blender 区）工作流

### 5.1 模式切换

- blender 区对话区顶部：`[低模 | 云API]` 切换控件，默认**低模**；旁边徽标显示云 API 配置状态（未配置 / 已配置）。
- 总结 agent 两种模式都参与，改写目标不同（见 5.2）。

### 5.2 发送链路：前置检查、总结 agent 与草稿

```
用户输入框发需求（口语化）
   ↓
前置检查（按当前模式，先于改写）：
  · 云API 未配置（缺模型/密钥）→ 发送即被拒绝，提示卡附"去设置"
  · 低模 Blender 链未就绪 → 发送即被拒绝，引导启动 Blender 并加载 MCP 插件 + 重新检测
   ↓ 检查通过
总结 agent 改写（用设置里配置的 Agent 模型，独立 system prompt）
   ↓
对话区出现「草稿卡」（虚线框，标注"优化后的提示词 · 双击编辑"）
   按钮: [发送] [取消]
   ↓ 双击进入编辑，改完再点【发送】
【低模】规划调用 → 「建造计划卡」（见 5.3）
   ↓ 计划确认
【两种模式】「存放位置」确认框（见 5.4）
   ↓
agent 开始执行
```

- **低模模式**改写目标：按附录参考提示词的结构产出专业长提示词——主题与视角 / 构图与底座 / 主体与候选清单 / 细节内容 / 美术风格 / 动效 / **产出结构要求（独立网格、命名、轴心、分层）** / 材质规定 / 禁止项 / 数量下限。
- **云 API 模式**改写目标：精炼的 3D 生成提示词（主体描述 + 风格关键词 + 负面词），适配文生 3D 接口。
- 草稿发送后成为正式指令进入对话历史；原始口语需求也保留在历史上方，便于回看。
- 总结 agent 与主 agent 的模型配置相互独立（设置中可分别选型，也可用同一服务商；总结 agent 未单独配置时回退使用主 agent 配置）。
- 前置校验只在用户**发起新消息**时触发；设置里修改了云 API 密钥 / 模型后，已打开页面不会实时重校验，新消息才会使用并校验新配置。

### 5.3 建造计划确认（低模模式）

- 草稿发送后，主 agent 先执行一次**只规划、不调工具**的模型调用，产出「建造计划」：分组（如底座环境 / 建筑外观 / 店内陈设 / 灯光特效，随题材增减）、每组物体清单（对照提示词的数量下限与产出结构）、每组验收标准（截图检查什么）。
- 计划解析失败自动重试 1 次；仍失败则降级为默认四分组（底座环境 / 建筑外观 / 店内陈设 / 灯光特效），不阻塞用户。
- 对话区出现「建造计划卡」：分组、组内物体清单、验收标准、预估步数；按钮 `[开始生成] [取消]`。v1 不支持逐组编辑，取消后可修改草稿重新发送。
- 计划确认后进入存放位置确认（见 5.4），随后按计划执行。
- 执行阶段按组推进：每组分「建造 → 自检」两个阶段；自检阶段由编排器注入指令，要求对照验收标准截图检查、缺漏补建；通过后进入下一组。
- 步数预算随计划动态计算：`maxSteps = 8 × 组数 + 10`（上限 60），不再使用固定值。

### 5.4 生成前「存放位置」确认框

- 树状展示资产库文件夹（根目录 + 任意层级子文件夹），支持对话框内"新建文件夹"。
- 默认选中上次使用的文件夹，首次为根目录。
- 确认后才真正开始生成（低模与云 API 一致）。

### 5.5 资产落盘结构

以资产名命名的子文件夹（示例 `sign_board_01/`）：

| 模式 | 内容 |
|---|---|
| 低模 | `xxx.fbx`（Unity 用）+ `xxx.glb`（预览用）+ `xxx.blend`（源文件，可继续改）+ `textures/` |
| 云 API | `xxx.glb`（原文件，兼预览）+ `textures/`（如有）；`.fbx` 在导入 Unity 时才由 Blender 转换生成 |

- 文件名由 agent 按规范生成**英文/拼音名**（如 `konbini_wall`），避免中文文件名兼容问题。

### 5.6 低模模式执行链

1. 前置检查：Blender 链就绪（发送时已校验，见 5.2；执行前断线则暂停自动重连；仍不满足 → 对话区引导："请先启动 Blender 并加载 MCP 插件" + 重新检测）。
2. 执行前确认：建造计划已确认（见 5.3）、存放位置已确认（见 5.4）。
3. agent 循环（Agent 模型 + Blender MCP 工具集），按计划分组推进：
   - 每组「建造」阶段：清理场景 / 建集合 → 逐步建模 → 材质贴图 → **视口截图回传对话区**（视觉闭环）；
   - 每组「自检」阶段：对照本组验收标准截图核查，缺漏或明显偏差就地补建修正；
   - 全部组完成后：导出 FBX + GLB → 保存 `.blend` → 落盘到目标文件夹。
4. 对话区实时显示：工具调用步骤卡（可折叠）+ 过程截图 + 当前组/总组数进度。
5. 结束后出「资产产出卡」：名称、面数、文件列表、[查看] 按钮。
6. **修改已有资产**：用户在文件树选中资产后直接说"把剑改短一点"（输入框显示目标资产 chip），agent 打开对应 `.blend` 继续编辑并覆盖导出同名文件；该路径不经过草稿、建造计划与存放位置三步，直接进入执行循环（v1 不做版本管理）。

### 5.7 云 API 模式执行链

1. 前置检查（发送时已校验，见 5.2；此处为执行前复查）：该服务商已选模型 + 已填密钥；不满足 → **拒绝本次对话**，提示卡附"去设置"直达按钮。
2. 按服务商提交异步任务：Tripo 直连 OpenAPI；混元走腾讯云 API（TC3-HMAC-SHA256 签名）。
3. 对话区进度卡轮询显示任务状态。
4. 完成后下载 GLB 落盘到目标文件夹 → 资产产出卡。
5. 云 API 资产**不支持对话修改**，只能重新生成（提示词中会说明）。

### 5.8 失败处理

- Blender 循环失败 / 超时 → 对应步骤卡标红 + [重试] 按钮；MCP 断线自动重连后继续。
- 云 API 失败 → 错误卡透传服务商原因（余额 / 限流 / 内容审核）+ [重试]（参数不变）；单任务超时上限默认 10 分钟。

## 6. Unity 区工作流

### 6.1 工程接入与激活互斥

- 顶部"导入"按钮 → C++ 唤起系统文件夹选择框（`dialog.pickFolder`）→ 校验 `Assets/` + `ProjectSettings/` → 激活。
- **全局唯一激活工程**由 C++ 内核以单例状态机维护：`未激活 → 激活中 → 就绪 → 切换中`。
- 切换工程流程（已有激活工程时再导入新工程）：
  1. 若旧工程有任务运行 → 确认框："当前工程有 N 个任务运行中，切换将终止这些任务"（无运行任务则直接切换 + 轻提示）。
  2. 断开当前 Unity MCP 会话 → **终止该工程绑定的所有 Agent 任务**（对话区对应消息标记"已中断：切换工程"）。
  3. 切换激活工程 → 建立新 MCP 会话（要求 Unity 编辑器已打开该项目；未打开则进入"等待 Unity 启动"状态并自动重试接入）。
  4. 文件监控重新指向新工程目录，**旧工程待处理的变更事件全部丢弃**，严防新旧 MCP 会话并行冲突。
- 影响范围：blender 区纯建模任务不受影响；跨界任务（如 glb 转换导入）会被中断并标记。
- 记住上次工程，重启自动恢复。

### 6.2 文件变更双源同步

- **外部手动改动**（用户在系统资源管理器新增脚本 / 贴图等）：C++ 用 Windows `ReadDirectoryChangesW` 递归监控激活工程 `Assets/`（及资产库），防抖 400ms → 推送 `fileTree.changed` 事件 → 前端文件树**局部刷新**。
- **Agent 经 Unity MCP 的改动**：直接采用 MCP 返回 / 通知结果做**定向更新**（操作涉及哪些文件是已知的）；该操作窗口内的文件监控事件被吞掉去重，不重复扫描。
- 监控忽略列表：`Library/`、`Temp/`、`obj/`、`Logs/`、`*.meta`（`*.meta` 由 Unity 自动生成，不显示也不推送）。

### 6.3 Unity 对话区

- 独立会话（与 blender 区完全隔离）。
- 可用工具集 = Unity MCP 工具：创建 GameObject、挂组件、改 Transform / 光源 / 材质、读写编译 C# 脚本、读 Console、截 Game 窗口。
- 执行流程：需求 → agent 循环（Agent 模型 + Unity MCP）→ 步骤卡 + **Game 截图回传对话区** → 编译报错自动回读 Console 继续修。
- 前置检查：Unity 链就绪，否则引导提示。

### 6.4 「添加资产」跨区联动

```
unity 区对话输入框旁 [添加资产] 按钮
   ↓
弹出资产选择器：展示建模资产库文件树（只列模型文件，支持多选）
   ↓
选中 → 输入框上方出现附件 chip（如 sword_01.glb ×）→ 随消息发送
   ↓
agent 处理链：
  · 附件是 .glb 且无配对 .fbx → 先调 Blender 链转换 glb→fbx（存回同一资产文件夹）
  · 附件是 .fbx → 直接用
   ↓
Unity MCP 导入资产 → 按用户要求实例化（坐标 / 命名 / 挂载）
   ↓
对话区回传操作结果 + Game 截图
```

- 转换步骤需要 Blender 链就绪；未就绪 → 提示"请先启动 Blender" + [重试]。
- **Blender 会话互斥（v1）**：低模 / 修改任务全程持有 `BlenderGate`（owner=`blender-agent`）；Unity 的无配对 GLB 转换以 owner=`unity-convert` 获取同一把门禁，多附件转换全程持有，结束即释放。门禁是单 owner 租约，不排队。
- 门禁被占用 → 立即返回 `error.card {reason:"blender-busy"}`（不新增 WS 方法 / 事件），文案提示"建模区正在工作 / Unity 正在转换，请等当前任务完成后再试"；用户稍后重试，系统不自动排队、不锁 ActivityBar。
- 反向同样成立：Unity 转换进行中在 blender 区发起低模 / 修改任务 → `blender-busy`；`plan.confirm` 被门禁拒绝时计划卡保留，可稍后再点 [开始生成]。
- 正常任务（blender 低模 / 修改 vs unity agent）不共享 Blender 会话，可并行；门禁只在"GLB→FBX 转换"与"Blender 任务"之间生效。
- v1 不做"建模完成自动导入 Unity"的流水线——一切由用户在 unity 区显式发起。

### 6.5 两区关系小结

| 维度 | blender 区 | unity 区 |
|---|---|---|
| 目录 | 固定资产库 | 自选工程 |
| 会话 | 独立 | 独立 |
| 工具 | Blender MCP + 资产写入 | Unity MCP + 资产导入 |
| 任务并发 | 每区同时 1 个；两区可并行 | 同左 |
| Blender 会话 | 低模 / 修改任务持有 `BlenderGate` | 仅无配对 GLB 转换时持有 `BlenderGate`；忙则 `blender-busy` |
| 唯一交互点 | 提供模型文件 | 添加资产选择器 + 自动转换 |

|---|---|---|

|---|---|---|

**保存配置即时生效规则**：已经正在运行的 Agent 任务继续沿用旧配置；只有新发起任务才使用更新后的模型 / 密钥，不强行中断正在执行的任务。

### 8.2 自研 MCP 客户端（C++ 学习核心）

- 实现 MCP 协议最小子集：`initialize` 握手 → `tools/list` → `tools/call` → 通知处理；传输层 = stdio（换行分隔的 JSON-RPC 2.0）。
- JSON 编解码用 QJsonDocument；进程 IO 用 QProcess 异步信号（readyReadStandardOutput 等）。
- 每个桥接一条会话；工具清单缓存 + 刷新；断线指数退避自动重连。
- 参考实现：Go 的 mark3labs/mcp-go 与 VS Code 的 TS SDK 行为对齐即可，协议本身不复杂。

### 8.3 前后端通信协议（WebSocket）

- 双向 JSON 消息；请求带 `id` 做请求-响应匹配；事件单向推送。
- 启动握手带随机 token（仅本机环回，防其它本机程序乱连）。
- 消息族示例：

```jsonc
// 前端→核心（请求）
{"id":17,"method":"chat.send","params":{"area":"blender","mode":"lowpoly","text":"做一个雨夜便利店街角场景"}}
// 核心→前端（响应）
{"id":17,"result":{"accepted":true,"taskId":"t_041"}}

// 核心→前端（事件）
{"event":"chat.delta","data":{"taskId":"t_041","text":"正在规划场景结构…"}}
{"event":"plan.created","data":{"taskId":"t_041","groups":[{"title":"底座与环境","items":["底座","排水沟与井盖","街角护栏"],"acceptance":"俯视截图：底座完整、街角 L 形转折清晰"}],"totalSteps":42}}
{"event":"tool.step","data":{"taskId":"t_041","stepId":"s3","tool":"execute_blender_code","status":"running","summary":"创建便利店墙体"}}
{"event":"fileTree.changed","data":{"area":"blender","reason":"incremental","paths":["道具/sign_board_01"]}}
{"event":"conn.status","data":{"blender":"ready","unity":"off","hints":{"blender":"已就绪 · 42 个工具"}}}
{"event":"log.append","data":{"level":"warning","category":"mcp","message":"bridge stderr: ...","time":"21:03:11"}}
```

- 方法族固定（参数在实现阶段细化）：`chat.send / chat.cancel / chat.clear / chat.retry / draft.send / draft.cancel / plan.confirm / plan.cancel / folderPick.submit / folderPick.mkdir / folderPick.cancel / fs.operate / file.read / assets.list / asset.import / project.select / project.switchConfirm / tree.refresh / session.load / settings.get / settings.save / env.check / bridge.restart / dialog.pickFolder`。
- 事件族固定：`chat.delta / chat.message / chat.image / tool.step / task.progress / asset.created / draft.created / plan.created / folderPick.open / fileTree.changed / conn.status / project.state / log.append / env.status / error.card / dialog.result`。
- v1 唯一的一对扩展：`dialog.pickFolder` / `dialog.result`。WebEngine 无法读取目录绝对路径，因此由 C++ 唤起系统文件夹选择框并回传路径；前端传自生成的 `requestId`，C++ 以 `dialog.result` 回传（取消也回传，不报错卡）。除此之外方法/事件族不再扩。
- 核心支持 `--headless` 模式（打印 WS 地址 + token），前端可在浏览器独立开发调试。

### 8.4 LLM 网关与 Agent 编排

- OpenAI 兼容协议一套通吃：流式 SSE 解析（QNetworkAccessManager readyRead）、tool_calls 循环、截图 base64 压缩（转 JPEG + 降采样）后回传。
- 工具清单**按区裁剪**：blender 区只带 Blender MCP + 文件工具；unity 区只带 Unity MCP + 文件工具，防工具过多选错。
- **工具桥接**：MCP `tools/list` 的 `{name, description, inputSchema}` 由 `ToolBridge` 转成 OpenAI `{type:"function", function:{name, description, parameters}}` 后再交给 `LlmGateway`；模型返回的调用统一收敛为内部 `{id, name, arguments(object)}`，回灌 assistant 历史时再转回 wire format（`type:"function"`、`arguments` 为 JSON 字符串）。`LlmGateway` 只负责流式聚合，不做 schema 转换。
- 总结 agent = 独立配置的模型（未单独配置时回退主 agent 配置）+ 独立 system prompt（模板内嵌附录参考提示词的结构骨架）。
- 主 agent 循环：LLM 决定工具 → C++ 执行 MCP 调用 → 结果 / 截图回喂 → 直到完成或失败；每步发 `tool.step` 事件给前端。
- **上下文组装**：`system + 本区最近 20 条历史消息（纯文本）+ 本次任务指令`；截图 base64 不回放历史；历史超预算从最旧截断。
- **截图回传**：工具结果中的图片压缩后双路使用——base64 回喂模型；同时发 `chat.image {area, taskId, dataUrl, caption}` 事件，前端在对话区渲染截图卡片。
- 低模执行前置一个**规划阶段**（见 5.3）：一次纯文本调用产出分组计划 → 前端计划卡确认 → 执行器按组「建造 → 自检」推进，组间自动注入验收指令；步数预算按计划动态计算。规划失败降级默认分组，不阻塞。
- 规划与执行共用主 agent 模型配置；Unity 区 v1 不启用规划阶段（架构预留开关）。

### 8.5 任务管理器

- 状态机：`排队 → 运行 → 成功 / 失败 / 已中断`；每区**串行队列**（同区不并行），两区可并行。
- 取消 = 协作式（agent 循环在工具边界检查取消标志）；切换工程 → 按"绑定工程"批量取消。
- 失败重试 = 保留参数重新入队。

### 8.6 进程与环境管理

- 桥接进程由 QProcess 拉起，内置两条默认命令（与当前开发机实测一致；写在配置默认值中，不占用设置页 UI，换包 / 升级时改配置即可）：
  - Blender：`uvx --python 3.11 mcp-for-blender`，附加环境变量 `UV_PYTHON_PREFERENCE=only-managed`；桥接再连 Blender 内插件 socket。
  - Unity：`uvx --from mcpforunityserver mcp-for-unity --transport stdio`；桥接再连 Unity 编辑器内的包服务。
- `uvx` 会自动拉取对应的 Python 包（首次运行联网下载，可能耗时数十秒，前端显示"连接中"）；本机须具备 Python + uv 环境（纳入 8.8 环境自检）。
- 桥接进程的 stderr 全部重定向到程序日志；**stderr 绝不能混入 stdout 的 JSON-RPC 数据流**（stdout 只承载协议数据）。
- 心跳检测（定时 ping / tools-list）+ 断线指数退避重连。
- 程序退出时确保桥接子进程全部终止，不留孤儿。

### 8.7 前端结构（Vue3 + TS）

- 组件：`ActivityBar / FileExplorer(树) / PreviewPane(three.js viewer、代码高亮、图片) / ChatPanel(消息流、草稿卡、计划卡、步骤卡、资产卡、附件chip；**每区一个常驻实例**，切区用 `v-show` 显隐) / SettingsDialog / StatusLights / 弹窗(存放位置选择、切换工程确认、添加资产选择器)`。
- Pinia 状态管理；markdown-it 渲染回复；highlight.js 代码高亮；three.js GLTFLoader + OrbitControls。
- dev：Vite dev server + 浏览器直连 WS（后端 `--headless`）；prod：vite build → qrc → `app://` 自定义协议加载。

### 8.8 运行前置条件（环境自检项）

- Blender（含 mcp-for-blender 配套插件）与 Unity（含 MCP for Unity 包）由用户自行安装，软件只通过 MCP 连接，不内置。
- MCP 桥接为 Python 进程：需要本机 Python + uv；自检页给出各依赖的检测结果与安装引导。
- 开发机：Qt 6（含 WebEngine 模块）+ MSVC + CMake；Windows 10/11。

## 9. 关键错误处理与边界

1. **MCP 断开**：状态灯黄 → 自动重连 → 持续失败则任务标失败可重试。
2. **文件写入竞态**：导出后校验文件大小稳定再触发下一步（防 Blender 未写完 Unity 就读）。
3. **FBX 轴向 / 单位**：Blender 导出预设 -Z 前向 / Y 上 / 缩放 1，Unity 侧对应导入配置。
4. **Unity 多实例冲突**：单工程互斥 + 切换先断旧会话；若 Unity 侧端口 / 实例冲突，引导用户保留目标工程的编辑器实例。
5. **云 API 波动**：透传服务商错误原因；单任务超时 10 分钟；可重试。
6. **LLM 幻觉**：agent 操作前先查询场景 / 工程实际状态，不凭记忆假设资产存在。
7. **安全**：WS 仅监听 127.0.0.1 + token 握手；密钥明文仅存本机配置文件。
8. **中文路径兼容**：资产文件与文件夹名由 agent 规范生成英文 / 拼音名。
9. **QtWebEngine 约束**：Windows 必须 MSVC 构建；打包体积约 150MB+（可接受）。
10. **Blender 会话互斥**：低模 / 修改任务与 Unity 的 GLB→FBX 转换共用 Blender MCP 会话；忙时返回 `blender-busy` 错误卡并提示等待后重试，不自动排队、不锁区。

## 12. 风险与坑点

1. Qt WebEngine：必须 MSVC；首次配置环境（Qt 在线安装器）需要一定时间。
2. 桥接链路长（Python + uv + 插件）：任一环缺失都会导致功能不可用——用环境自检 + 状态灯 + 引导兜住体验。
3. 聊天区网页化后，聊天内容与三步确认流（草稿 / 存放位置 / 工程切换）是交互复杂度最高的部分，建议前期先用简化版快速联通，分期打磨。
4. 混元 TC3 签名实现是云适配层最容易出错的部分——单测覆盖 + 官方示例对齐。
5. LLM 长提示词 + 截图回传的 token 开销：截图统一压缩，工具结果超长时截断。
6. **ReadDirectoryChangesW 缓冲区溢出**：高频文件变更（批量生成 / 复制资产）可能触发事件溢出；监控模块做事件队列限流、合并去重，超限事件丢弃并写日志；发生缓冲区溢出（界面树可能已与磁盘不一致）时补一次全量刷新兜底，防止 WebSocket 消息风暴压垮前端。
7. **GLB→FBX 转换会重置 Blender 场景**：转换脚本使用 `read_factory_settings(use_empty=True)` 清空当前场景。v1 的 `BlenderGate` 只能防止应用内任务与转换并发，无法保护用户手动编辑但未保存的场景；转换前应保存。彻底方案（独立 headless Blender 进程）留待后续阶段。

## 13. 附录：总结 agent 参考提示词（低模模板基准）

> 来源：用户此前手写、且实测生成效果良好的提示词。低模模式总结 agent 的 system prompt 模板以其结构为骨架（可适配不同题材；云 API 模式另行精简）。完整原文如下：

主题与视角：请制作一个雨夜便利店街角小场景。以第三视角俯瞰观察整个场景，整体像一个可以自由拖拽、旋转、缩放观看的微缩三维模型 / 小型景观。画面中不得出现任何 UI 界面元素（无网格线、无坐标轴、无操作手柄、无水印、无边框按钮）。

底座与构图：地面为一个完整的正方形底座，所有元素都搭建在这个底座上。构图紧凑、层次清晰，整体呈现出小巧、精致、可收藏的模型感。街角位于底座的视觉中心偏一侧，形成明确的 L 形或弧形街角转折，像日本动画里常见的夜晚社区一角。街道尺度不必大，但要有近景（路边物件）、中景（便利店本体）、远景（巷口与远处灯光）三层纵深。

场景主体：日式便利店街角。便利店位于视觉中心，外部包含典型的日式街角元素（以下为候选清单，按需选用，宁精不多，避免堆砌）：便利店招牌、玻璃橱窗、自动门、屋檐雨棚、门口地垫、自动贩卖机、自行车、雨伞架、垃圾桶、路灯、电线杆与电线、路牌、街角护栏、停车位标线、排水沟与井盖、积水路面、反光斑马线、小巷入口、空调外机、小型公告栏或海报栏、快递柜或投币储物柜。

店内内容（重点）：不要人物。但便利店内部必须有充足内容，且能透过大面积玻璃窗清楚看到店内。店内陈设包括：整齐排列的货架、饮料柜、便当区、饭团与零食陈列、收银台、咖啡机、杂志架、宣传海报、店内灯箱、冰柜、关东煮柜台、地面导视贴纸、储物柜或后场门、天花板灯盘与吊挂 POP。室内要显得明亮、温暖、真实、充实，与室外潮湿昏暗的雨夜形成鲜明对比，营造典型的日式动画雨夜氛围。

美术风格：高精细建模 + 三渲二卡通渲染。清晰的轮廓线（外轮廓略粗、内部结构线略细），干净平整的材质表现，色彩柔和但富有夜景霓虹的层次感。强调湿润的夜景反光：路面水膜反射招牌与路灯、玻璃上有雨水滑落痕迹、金属与塑料有克制的高光。暖色室内灯光与冷色雨夜街景形成冷暖对比。整体气质安静、治愈，带一点都市夜晚的孤独感但依然温暖，像一幕被定格下来的日本动画街角场景模型。

动效（细微、循环、不抢戏）：持续降雨（实现方式见下方「雨水特效要求」）、屋檐滴水、地面积水涟漪、便利店招牌或灯箱轻微闪烁、自动门偶尔开合、雨水沿玻璃滑落、路面积水反射随光线微弱变化、远处交通信号灯或对面窗户灯光有极缓慢的明暗变化。整体仍保持"静止而精致的微缩世界"观感，动态只作为生命力点缀。

雨水特效要求（重要）：雨水必须实现为 Blender 粒子系统动态特效，不生成任何网格几何体；禁止用长条平面 mesh 或任何片状几何体冒充雨丝。视觉效果：雨丝细密、下落方向一致，带沿下落方向的运动模糊拖尾（而非一根根清晰的静态细条）；遵守透视近大远小；半透淡白色，可被场景灯光微弱染色；均匀布满空间，但不得遮挡场景主体与便利店橱窗视线。雨水整体作为可单独隐藏的特效图层存在，不进入可选中物体清单。

产出结构要求（重要）：独立产出原则：场景中每一个可辨识的物品都必须作为独立的网格 / 独立物体产出，不得合并为单一整体模型。同一类物品之间也必须彼此独立（例如两辆自行车是两个独立物体，三个货架是三个独立物体，多根电线杆各自独立）。必须独立的清单：便利店建筑本体（含墙体、门窗、雨棚）、招牌与灯箱、自动贩卖机、自行车、雨伞架、垃圾桶、路灯、电线杆、路牌、护栏、空调外机、公告栏、井盖与排水沟、店内货架、饮料柜、冰柜、收银台、咖啡机、关东煮柜台、杂志架、地垫、海报与灯箱画面、地面标线。允许合并的部分：底座地面（含路面、积水层、标线可作为同一物体的子面或独立贴图通道）、雨水粒子系统（纯特效，不生成网格几何体，不列入可选中物体清单）、电线（可作为一条连续曲线/线缆独立于电线杆）、海报上的文字与图案（作为贴图而非独立几何体）、雨滴拖尾、溅落水花与水波纹（作为粒子/着色器特效而非实体模型）。

层级与命名：按「底座 / 建筑 / 室外道具 / 室内道具 / 灯光 / 特效」分组建立层级；每个物体使用可读的英文或拼音命名（如 konbini_wall、vending_machine_01、bicycle_02），同名类物品用数字后缀区分。

轴心与摆放：每个道具的轴心落在其底部中心或与地面的接触面上，保证放到平面上不会悬空；尺寸比例统一，以便利店入口高度为基准保持一致性。

材质与贴图：每个独立物体可单独指定材质，同类物体允许共用材质球但必须是可分离的实例；霓虹与灯箱部分使用自发光通道单独控制，以便独立调节闪烁强度。

可选扩展：如支持，请同时提供简化版 LOD 与基础碰撞体；允许单独隐藏室内、隐藏雨天特效、隐藏招牌灯光，以便分层展示。

数量下限：最终场景应包含不少于 25 个可单独选中的独立物体（不含底座与雨水特效），其中店内可见陈设不少于 10 个。

禁止项：无人物、无动物、无 UI 元素、无真实品牌 Logo 与可识别商标（招牌文字使用虚构店名或日文假名占位）、无过度繁复的装饰导致画面杂乱、无任何形式的雨丝网格（长条平面、交叉片、透明条带等一律禁止，雨水只能以粒子系统呈现）、无将全部道具合并成一个不可拆分的整体模型。
